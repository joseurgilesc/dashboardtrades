## Deviations from Design

1. **Firebase web config values are placeholders.** `design.md`/`proposal.md` name only `projectId: tradingdashboard-7425a`; `apiKey`, `messagingSenderId` and `appId` are absent from planning artifacts. `js/firebase.js` originally shipped `REPLACE_WITH_*` placeholders, but the live values were later filled in (project `tradingdashboard-7425a`) at the user's direction before this batch. Treat them as real client identifiers, not secrets.
2. **`js/firebase.js` is loaded but `init()` is invoked by the app boot.** Task 1.2 required SDK init + `enablePersistence`; the call is made from `boot()` (Phase 2), not at script load, so the PR 1 slice stayed inert. Phase 2 now wires it.
3. **Extra markup IDs beyond the design's named three.** `#authEmail`, `#authPassword`, `#btnEmailAuth`, `#btnToggleAuthMode`, `#authTitle` and `#userBox` were added so the gate is functional; the design only named `#authForm`, `#btnGoogle`, `#authError`, `#btnLogout`, `#userEmail`.
4. **`Store.detach()` added (not named in tasks).** Task 2.4 names `attach`/`subscribe`; `detach()` is required so logout and user switching cannot leak in-memory data across accounts. It is the inverse of `attach` and clears state to empty.
5. **Non-allowlisted sign-out surfaces through the signed-out event.** `onAuthStateChanged` signs out a denied account and carries the denial reason on the resulting `null` event (module-level `pendingDenial`) so the UI can explain the refusal without a second, contradictory "signed-out" state. This is the design's "not invited + sign-out" behavior, implemented centrally in `firebase.js`.
6. **`clearAll`/`seedSample`/`importJSON` persist via `persistAll(previousIds)`.** These bulk operations set the new trades/meta and delete documents that no longer exist. `importJSON` keeps its existing "replace" semantics.
7. **`Store.canPersist()` retained but no longer gates boot.** localStorage is no longer the source of truth (Phase 3 migrates `bpt.journal.v1`), so the boot-time "changes will not be saved" warning was removed. The helper remains exported.

## Issues Found

- No Firebase web config values existed in the planning artifacts at PR 1 time (see Deviation 1); this is now resolved with the real project values.
- The design's compat-equivalence claim is confirmed against the real artifact: the pinned `firebase-firestore-compat.js` `12.18.0` exposes `enablePersistence(e)` and accepts `{ synchronizeTabs }`; the modular `initializeFirestore`/`persistentLocalCache` names are absent from the compat build. No compat API deviation to report.
- **`auth/web-storage-unsupported` is in the popup→redirect fallback set.** Redirect sign-in also requires web storage, so this code may not actually be recoverable by redirect; it is included because the redirect attempt is the only remaining SDK path, and a failure surfaces as an actionable error. Flagged for manual verification.
- **Partial migration can strand the local key.** If a trade chunk commits and a later chunk fails, a retry sees the account already has trades and skips migration, leaving `bpt.journal.v1` in place with the account partially populated. The key is only removed after all batches succeed, so no local data is lost, but recovery is manual. Flagged for Phase 4 manual verification.
- **Failed reauth after purge leaves an empty account.** Because data is purged before `user.delete()` (required by rules), a subsequent reauth failure leaves the account with no documents and no session change. The UI reports the failure and the user can retry; no local data is lost. Consider a "recent login" pre-check in a future revision.
- **The rules test could not be executed in this environment.** Java and the Firebase CLI are absent, and the Firestore emulator requires Java. The test file's syntax, JSON configs, and the `@firebase/rules-unit-testing@5.0.2` API surface were verified, but the 15 assertions have not been observed to pass. This is the single largest open verification item.
- **`firebase-tools` is a heavy devDependency.** `npm install` pulls a large tree only to run the rules test. This is acceptable because it is dev-only and `node_modules/` is ignored, but it is worth noting for reviewers.
- **Email verification had no sender before PR 6 (the real gap).** Rules and `checkAccess()` require `email_verified == true`, but the app never sent a verification email, so an email/password user was permanently denied with reason `email-unverified` and could not recover from inside the app. Google sign-in worked only because Google emails arrive pre-verified. PR 6 closes this: verification is sent on sign-up, can be resent, and the user can re-check after clicking the link.
- **`sendEmailVerification()` is called with no `ActionCodeSettings` (PR 6).** The default Firebase verification page is used; the user verifies in their inbox and returns to the app tab to press "Ya verifiqué mi correo". No continue URL is configured, which avoids `auth/unauthorized-continue-uri` on unauthorized origins.
- **The verification flow is not live-verified.** The 34/34 harness run proves the SDK-call wiring, guards, and state transitions against a stub, but not real email delivery, the inbox link, or a live `user.reload()` reflecting `email_verified` from the Rules perspective. This belongs to manual task 4.2/4.3.
