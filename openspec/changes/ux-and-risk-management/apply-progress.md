### PR 6 batch (retained)

- [x] 5.1 `js/store.js`: reworked pure `computeRisk` to the confirmed BPT method. `tickValue = tick × pointValue`; `P_m = stopTicks × tickValue`; `dailyBudget = (dailyRiskPct / 100) × capital`; `perTradeRiskPct = dailyRiskPct / tradesPerDay`; `perTradeRisk = (perTradeRiskPct / 100) × capital`; `contracts = floor(perTradeRisk / P_m)`. `tradesPerDay` is the per-account `dailyTradeLimit` (default 3 when missing/non-numeric) and is guarded to 1 for `0`/negative, so the divisor is never zero. Commission is reported separately (`commission`) and is never folded into `P_m`. The return shape is additive: `dailyBudget`/`budget` (alias), `dailyRiskPct`, `tradesPerDay`, `perTradeRisk`, `perTradeRiskPct`, `tickValue`, `stopTicks`, `pm`/`riskPerContract` (alias), `commission`, `contracts`, `viable`, `minBalanceForOneContract`, `size`. Two small helpers were added: `resolveStopTicks` (explicit `stopTicks` wins, else legacy `stopDistance` points ÷ `tick`) and `resolveTradesPerDay` (default/guard). `minBalanceForOneContract` was aligned to the same tick/per-trade model.
- [x] 5.2 `index.html` + `js/app.js`: the Registro **Calculadora de riesgo** panel now works in ticks. The stop input is `#riskStopTicks` (ticks, default 8) and the results show `Capital`, `% Riesgo diario`, `Operaciones al día`, `Presupuesto diario`, `Valor del tick`, `P_m (pérdida máx./contrato)`, `Riesgo por operación`, `Contratos`, `Comisión (ida y vuelta)`, `Riesgo de la posición`, `R/R` and `Recuperación requerida`, all reusing the existing `.preview`/dark tokens in the same card. `renderRiskPanel` reads the account's current balance (capital), configured daily `riskPct` and `dailyTradeLimit`, derives `tickValue` from `INSTRUMENTS`, and still converts a recorded stop price to ticks (`|entry − stop| / tick`) so it takes precedence over the tick input. The viability warning now names the daily risk, the trades/day split and the per-trade budget. The `wireEvents` live-input list swaps `riskStopDistance` for `riskStopTicks`.
- [x] 3.5 (re-baselined): the manual `risk-calculator` verification scenario was rewritten from the superseded points+commission method to the BPT method (10000 / 3 % / 3 trades / 8 ticks ES → 300 daily / 100 per-trade / 100 P_m / 1 contract; daily-budget division → 3; below-P_m → 0 + warning).

## Deviations from Design

1. **PR 1 — strategy display names combine the spec and prompt wording** (`Box Breakout (Ruptura de laterales)`, `Tres Impulsos (Ruptura con tres impulsos)`, `Figuras Chartistas (HCH y dobles/triples)`); other names unchanged.
2. **PR 1 — CSV export adds a read-only `strategyName` column** while `strategy` keeps the id, so import round-trips.
3. **PR 1 — instrument `hours` carry an inline "por verificar" marker** for unverified FDAX/FDXM data.
4. **PR 1 — `getStrategies()` returns copies** (defensive, matches `getTrades()`/`getBalances()`).
5. **PR 1 — legacy seed coverage removed** (task 1.6 used only named ids); legacy chart path must be exercised via a manually added/imported `E1..E5` trade.
6. **PR 2 — `clampDailyLimit` added as a pure helper.** Task 1.8 only named `clampRiskPct`, but 2.5 requires daily-limit validation; keeping it pure in `store.js` follows the "all logic pure" constraint instead of inline UI parsing.
7. **PR 2 — `computeRR` accepts an explicit `minRR` but falls back to `getMinRR()`** (the configurable global in `settings.minRR`, default `DEFAULT_MIN_RR`). The design did not specify where `minRR` lives; the Ajustes min-RR field (2.13) makes it a global setting.
8. **PR 2 — `recoveryPct` returns the ratio per the spec formula** (`0.5 → 1`, displayed as `100 %`); the UI multiplies by 100. The panel derives the drawdown fraction from `totalRisk / currentBalance`, since the assigned slice specifies no separate drawdown input.
9. **PR 2 — `stopDiscipline`/`intradayDrawdown`/`losingStreak` accept `(trades, account)` and also tolerate `(account)`** (uses store trades), so both the pure call style and the `tasks.md` shorthand work.
10. **PR 2 — `intradayDrawdown` bases its percentage on the start-of-day equity** (initial balance + net of earlier trades) and warns at ≥ `DAILY_DD_WARN_PCT` (5 %); `losingStreak` uses the existing KPI loss definition (`net <= 0`).
11. **PR 3 — balances visibility delivered via header chip sublabels only.** The prompt allows "header chip sublabels and/or a compact Registro card"; the chips (current value + initial sublabel + combined total) satisfy every `balance-visibility` scenario, so no extra Registro capital card was added, keeping the diff focused.
12. **PR 3 — `dailyLimitStatus.exceeded` is literal `count >= limit`.** A stored limit of 0 therefore warns immediately ("at the limit"). The spec defines warning behavior only for positive limits and explicitly allows 0 to be stored; the literal reading matches the spec's "reached or exceeded" wording. Documented so verify can confirm the intent.
13. **PR 4 — `trade.target` and `trade.plannedRisk` are monetary (USD) amounts, not price levels.** The spec scenario (`planned risk 100`, `target 300` → `3:1`) and the assigned slice's literal `computeRR({plannedRisk,target})` both require `target / plannedRisk` to be dimensionless, so the form labels them `Objetivo (USD)` and `Riesgo planeado (USD)`. `trade.stop` stays a **price** (the slice says "when a stop price is entered"), used for the `Sin stop` flag and the derived stop distance.
14. **PR 4 — the recorded stop drives the stop distance without mutating the calculator input.** `renderRiskPanel` uses `|entry − stop|` when both are present and otherwise falls back to `#riskStopDistance`; it does not overwrite the input, so a manual calculator distance remains usable and no stale value survives a cleared stop. Documented in the panel hint.
15. **PR 4 — recorded `plannedRisk`/`target` override the calculator's computed total risk / own target input**, while the recovery display stays based on the computed `totalRisk` (keeps it consistent with the "Riesgo total" item). The calculator inputs remain the fallback when no trade values are recorded.
16. **PR 4 — `trade.stop`/`target`/`plannedRisk` are not added to the CSV export** (the existing CSV already omits `stop`). JSON export includes every trade field automatically, and the harness proves the JSON round-trip. Keeping CSV unchanged avoids widening the slice.
17. **PR 5 — `dailyScalingPlan` returns an object with a `rows` array plus `finalCapital`** (not a bare array). The task wording ("returning an array ... and the final capital") is satisfied by a wrapper: `rows` feeds the table and `finalCapital` feeds the summary without a second call.
18. **PR 5 — the panel lives in the Dashboard, not Ajustes.** Ajustes holds persisted settings and data management; the scaling plan is a read-only projection that complements the KPIs/charts, so the Dashboard is the better fit.
19. **PR 5 — `rr`/`days` default inside the pure function and `days` is capped at 365 (`SCALING_DAYS_MAX`).** The cap is a safety guard against a mistyped day count freezing the UI; `clampedDays` reports it so the summary can say so. Only the fallbacks are constants — the model numbers are always the configurable inputs.
20. **PR 5 — the panel seeds capital/risk % from the entry form's selected account but never auto-overwrites user edits.** Changing the account does not clobber custom scaling inputs; the user edits the fields directly.
21. **PR 6 — `Capital`, `% Riesgo diario` and `Operaciones al día` are display-only in the Registro panel.** They come from the selected account's current balance and the Ajustes per-account settings; making them editable in two places would create two sources of truth. Ajustes stays the single edit point.
22. **PR 6 — `Valor del tick` is derived from instrument metadata and shown read-only.** `tickValue = tick × pointValue` is instrument data, not a user choice; the only new BPT input is the stop in ticks.
23. **PR 6 — `computeRisk` keeps `budget` and `riskPerContract` as aliases** of the new `dailyBudget` and `pm` so the return shape stays additive, but the points+commission formula is gone. The primary fields are the BPT ones.
24. **PR 6 — `resolveTradesPerDay` defaults a missing/non-numeric value to 3 and maps any numeric `< 1` (including the allowed stored `dailyTradeLimit` of `0`) to 1**, honouring "never let `tradesPerDay` be 0" while keeping the per-account default.
25. **PR 6 — task 3.5 was re-baselined** from the superseded points+commission scenario to the BPT method. The delta spec `specs/risk-calculator/spec.md` still documents the old formula (see Issues) and needs a `MODIFIED` delta before verify/archive.
26. **PR 6 — `minBalanceForOneContract` was aligned to the tick/per-trade model** even though the prompt only named `computeRisk`; leaving it on the old formula would have made the two exported calculators disagree.
27. **PR 7 — the last-used values live under a single nested `settings.lastEntry` object** (`{account, instrument, strategy, direction, emotion}`) instead of five top-level settings keys. `setSettings` is a shallow merge, so one nested object keeps the write atomic and the read a single `getLastEntry()` normalization.
28. **PR 7 — validation runs on both write and read.** `saveLastEntry` ignores incoming values not present in the catalog (keeping the previous valid one), and `sanitizeLastEntry` (used by `getLastEntry`) falls back to the first catalog value for stale/unknown stored data, so a select can never receive an option it does not have.
29. **PR 7 — `duplicateLastTrade` leaves `tradeNumber` empty** (the literal "no tradeNumber" from the slice); `handleSubmit` assigns the next number on save, as it already does for any new trade. "New id" is proven by `state.editingId === null` plus a distinct id on the saved record.
30. **PR 7 — the duplicate copies only the setup fields named in the slice** (account, instrument, strategy, direction, emotion, contracts, target, stop). `plannedRisk` and `notes` are intentionally not copied; the "Más opciones" disclosure opens automatically when a target was copied so the value is visible.
31. **PR 7 — `resetForm` re-collapses "Más opciones"** (a new trade starts from the default collapsed state) while `handleEdit` opens it when the trade actually uses `target`/`plannedRisk`/`notes`, so editing never hides existing data.
32. **PR 7 — `getLastTrade` picks the highest `tradeNumber`** (later array position wins ties) rather than the latest array position, matching the journal sequence shown in the table.
33. **PR 7 — the contracts prefill skips a zero suggestion** (leaves the field blank for the user to fill) and is a default only: it never disables submit and the user can always override it.
34. **PR 7 — `Store.clearAll()` resets the whole state, including `state.settings`**, so "Borrar todo" also clears `lastEntry` (and the risk settings). This is pre-existing behavior and was left unchanged; the harness re-establishes `lastEntry` after `clearAll` to reflect that.
